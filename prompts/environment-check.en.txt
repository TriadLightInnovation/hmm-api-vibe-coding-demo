==================================================
7. Offline tests and UI launch/close verification
==================================================

Read the test entry points before running them.

Offline tests must not call:
- initialize.
- setParameters.
- startScan.
- stopScan.
- Callback registration APIs.
- AO, laser, stage, or firmware operations.
- Other native HMM hardware APIs.

This restriction applies to startup, test execution, error recovery,
and shutdown—not only button clicks.

Run the existing hardware-free functional and ABI tests.
Examples may include:
- Struct layout checks.
- Geometry and timing calculations.
- Frame assembly.
- Averaging.
- Composite.
- State handling.
- Logging and deployment.

Use the actual available tests.
Do not invent tests or copy historical test counts.

Verify normal offline Release UI launch and close.

Run the existing --ui-smoke entry point or its documented equivalent:
- Five consecutive Debug runs.
- Five consecutive Release runs.
- Sequentially, in fresh isolated processes.

A run passes only when:
- Expected test actions complete.
- Required artifacts are produced by this run.
- The process exits normally with the expected success code.
- No unhandled exception is recorded.
- No test child process remains running.

Use per-run identifiers to reject stale reports or screenshots.

A screenshot or PASS JSON written before shutdown is not enough.
The parent test runner must observe the final process exit.

A timeout or forced termination is FAIL.

If no safe UI test path exists, inspect whether a minimal test-only harness
can be added in the working copy without changing production acquisition.

Do not introduce a silent fake-hardware fallback.
If offline safety cannot be established, report the relevant test as
NOT TESTED and explain the blocker.


==================================================
8. Minimal fixes allowed during environment acceptance
==================================================

This phase may correct, in the working copy only:
- Portable path/deployment issues.
- Environment/build/test script defects.
- Small, clearly isolated offline test-harness defects.

A previously encountered failure pattern was:
A WPF smoke harness lacked a running Dispatcher event loop, and an
asynchronous continuation called Window.Close from a worker thread.

This is a known pattern to check, not a predetermined diagnosis.
If the supplied template already contains the fix, verify it; do not reapply
or rewrite it unnecessarily.

For an actual failure:
1. Preserve the original logs and exit code.
2. Capture the exception type, message, stack, and source location.
3. Identify the calling thread and the owner of the affected UI object.
4. Establish whether the defect is test-only or in shared production code.
5. Apply the smallest permitted fix.
6. Rerun affected tests and the full required acceptance.

UI-affine test operations must run on the owning Dispatcher.
The test must allow the real WPF event loop to run.
Observe window closure, application exit, and final process termination
without creating a circular wait.

Do not:
- Catch and ignore the exception.
- Force Environment.Exit(0) to hide a broken shutdown.
- Remove smoke testing from acceptance.
- Use arbitrary extra sleeps as a substitute for synchronization.
- Disable verification flags.
- Report PASS before process exit.

If resolution requires changes to shared acquisition, native ABI,
hardware shutdown semantics, or substantive production behavior:
Stop that modification and report it as a separate blocker.
Do not expand this environment task into a core rewrite.

Store all repair patches and evidence under Environment.
